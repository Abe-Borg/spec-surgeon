# Spec Surgeon v0.4.0 — hands-on sweep against the author's expectation list

Date: 2026-10-15. Branch: `claude/intelligent-meitner-xj6e52` from `master` at `31af40b` (v0.4.0). Input: Abraham's
nine-part list of what the program should do, refuse or get wrong ("everyday requests", "the architect's spec as the
template", "fonts and sizes", "inserting and deleting paragraphs", "traps", "requests it can't do", "safety features",
"messy batches", "rendering, the window, settings and updates"). Deliverables: this report, the fixes in `src/`, and
`tests/test_sweep_fixes.py`, which pins every fix.

## 1. Method

The container has no Anthropic API key and no Word, so the Claude layer and Word COM stayed untested (both were
already marked [unproven]). Everything else was driven for real:

1. **Fixtures.** The repository's synthetic fixtures (`tests/make_fixtures.py`: the plain cover+body specs, the rich
   op fixture, the sized fixture, the architect's "08 71 00 - DOOR HARDWARE (ACME)" template spec) plus three new
   families built for this sweep: a realistic discipline spec holding every phrase the list names (an issue stamp in
   the header, "NFPA 13, 2022 Edition" in the body, the header and inside a TOC field, "Marshall … shall",
   "or approved equal", curly quotes, a phrase that is partly bold, editor's notes in a `CMT` style, a text box, a
   table, Century Gothic 9 pt); twelve variants of the architect's spec (a title in another case, by STYLEREF, an
   extra header line, "087100", "08-71-00", a header laid out in a table with a logo and "Page X of Y", a title in
   a text box, different odd & even pages, a tracked insertion in the header, a one-word "DOORS" title with
   "OUTDOORS PAVILION", no SECTION line in the body); and target variants (a landscape schedule section, a title
   split over two lines, "211313" instead of "21 13 13", a Related Sections line in capitals, no SECTION line).
2. **The EditSpec each request compiles to.** For every row of the list the spec the compiler would produce (per
   the catalog rules and the system prompt) was written by hand and run through `spec-surgeon plan-spec` and
   `spec-surgeon run-spec` (`--no-render`, then with LibreOffice for the geometry checks), and the output XML was
   read — paragraph by paragraph, with revision markers — rather than trusting PASS.
3. **The safety rows** through `run-spec --in-place` with a Word lock file, a read-only file, a renamed `.txt`, a
   truncated zip, `.doc`/`.docm` files and a `~$` lock in the folder; the preview → edit → Run rows through
   `gui.Session` (the window's logic, no Qt); settings corruption through `settings.load_settings`.
4. **A read of every module** (`cli`, `editspec`, `catalog`, `compiler`, every op, `ooxml`, `package`, `batch`,
   `guard`, `gui`, `preview`, `planner`, `report`, `profile`, `fingerprint`, every `verify/` module, `render/`,
   `ui/app`, `ui/update_ui`, `ui/settings_dialog`, `ui/worker`, `ui/rows`, `updater`, `settings`, `winapp`,
   `credentials`, `codegen`, `sandbox_runner`, `advisor`, `agent`, `jobs/`, `xsd`) looking for silent-wrong-result
   paths first, crashes second, awkwardness last.
5. Baseline suite: `python3 -m pytest -q` → 315 passed, 1 skipped (the Windows Credential Manager test) once Qt's
   system libraries are installed; 301 passed, 15 skipped before (the window tests skip without `libEGL`).

## 2. Headline

- **No silent data loss was found.** Every edit the engine delivered matched its prediction character for character;
  every "wrong" outcome in the list (Marshall → Marmust, curly quotes not found, the title's first line only) is a
  predicted, visible outcome the preview shows. The traps that must refuse did refuse (a phrase inside a TOC field, a
  phrase partly bold, a find that spans a tab, the architect's number written another way, a STYLEREF title, a text
  box, odd/even mismatch, "DOORS" inside "OUTDOORS").
- **One safety hole (S1):** the approval token did not cover the template spec. Preview, then save a new version of
  the architect's spec, then Run → the run went ahead with the new template and nobody had seen it. Fixed.
- **Two things the engine refused badly (S2, S3):** a request it should refuse at plan time ran to V10 and failed
  there on every file; a request it should accept refused a whole batch over one single-section file.
- **One crash path on Windows (S4):** a read-only spec with write-back would have raised a raw `PermissionError`
  out of the batch after other files were already written; on Linux as root it was written back. Fixed.
- Two cosmetic items (S5, S6). The rest of the list behaves as written.

| # | Finding | Where | Fix |
|---|---|---|---|
| S1 | The approval token hashed the spec and the batch files but not the template file. A template spec edited or replaced after the preview ran un-previewed (the plan's md5 pin protects only plan→apply within one run; the window and `run-spec` re-plan from scratch). | `preview.approval_token` | hashes every template the spec reads: path, size, mtime, content md5. `Session.run`, `run-spec --approval` and the Tier B key go through the same function. |
| S2 | `set_font` / `set_paragraph_props` declare touches only for parts where they change something, so a font op whose scope covered the headers another op removed had no conflict with `remove_header_footer`; the plan was clean and V10 failed with "run_fonts: word/header1.xml missing from the output" on every file (visible in the preview's sample verdicts, but after the fact). | `ops/set_font.py`, `ops/set_paragraph_props.py`, `ops/base.check_conflicts` | both ops add a `(part, "scope", "verify")` touch for every part in scope; rule 1 (whole-member removal vs any touch) now fires, with a hint naming the op to narrow; two `verify` touches of one part never conflict (rule 2 exemption). |
| S3 | `unknown-slot` compared the fill rules with the slots of the template parts *this file* uses; a single-section spec in a batch mapped to a cover+body template uses the cover's parts only, so the body's rules were "unknown" — and since the code is fatal for the compiler, one such file rejected the batch's spec. | `ops/apply_header_footer_template.plan` | the rules are compared with the slots of every template section named in `template_sections`; a rule naming a slot nowhere is still `unknown-slot` on every file. |

| S5 | A pure tracked deletion left `plan.diffs` empty (the words stay as `w:delText`), so `summarize_plan` said "text: no block changes text". | `planner.summarize_plan` | "N block(s) get a tracked deletion (the deleted words stay visible as a redline until accepted)". |

## 5. Design notes (recorded, not changed)

- **A. A hit inside a field refuses the file.** `replace_text` raises `field-result` for an occurrence inside a
  field instruction or cached result, which refuses the whole file even when the other occurrences are plain text.
  That is what the list expects ("a phrase inside a cross-reference or TOC field → refused"), and the TOC result is
  refreshed by Word anyway; a `skip_fields` option (skip that occurrence, flag it) would let the rest of the file
  through. Left as a candidate.
- **B. Targeted paragraph formatting is tracked by default.** "justify all body paragraphs" compiled with
  `{"in_table": false}` makes 34 tracked `pPrChange`s; the op's schema says so and `tracked: false` turns it off.
  Whether the compiler's system prompt should steer "body paragraphs" to plain formatting is a wording decision.
- **C. Section-specific words in the architect's header** other than the number and title ("FINISH HARDWARE") are
  copied into every spec with no flag; the ⟦ ⟧ notes are the place to look, as the list says.
- **D.** `expand_inputs` takes a folder's top-level `.docx` files only (no sub-folders); a CLI argument naming a
  single file of another extension is accepted as given.
