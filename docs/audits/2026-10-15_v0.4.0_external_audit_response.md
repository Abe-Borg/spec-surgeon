## 1. What the audit looked at, and what had moved since

The audit ran at `3977ad9`, before PR #4 (template specs, font sizes) and before PR #6 (the hands-on sweep). Two of
its sections are therefore out of date on `master`:

- **"The checklist describes features missing from this checkout."** Template specs (`slot_markers: ["reference"]`,
  the number and title safeguards, `match-template-spec-header-footer.json`) and font sizes (`size`, `size_from`,
  `effective_font` with a size) exist since PR #4 and were exercised row by row in the 2026-10-15 sweep. Nothing to
  do there. Its point about the Tier B "make PART headings bold" fallback is right and is recorded below as a
  design limit, not a bug.
- **F3 and F7** were fixed by the sweep (S1: the approval token covers the templates; S4: a refused write-back is that
  file's V9 failure, never a crashed batch). The sweep's tests pin them.

Every other finding was reproduced on `master` before any code changed — F1, F2, F4, F5, F8a, F9, F10, F12, F13 and
the Strict Open XML `AttributeError` by running the engine on synthetic files built for each case, F6 and F14–F17 by
reading the code paths the report names and probing the behaviour (a relative sandbox folder, an injected verifier
exception, an unreadable advice input, a non-numeric margin). The audit's descriptions were accurate in every case.
Its batch-plumbing probes were sharper than the sweep's: the sweep used one folder, explicit footers, a one-paragraph
TOC and two sections, which is exactly where F1/F2, F5, F9 and F10 hide.

## 3. Deferred or disagreed

- **F11 — a target whose `Header` style carries `w:vanish`.** Real, rare, and rendering on catches it (the audit's own
  run quarantined it). Modelling visibility on both sides is more work than it buys at this stage; recorded as a
  known limit. Rendering on is the recommendation for templating runs anyway.
- **F8b — stale outputs when a results folder is reused by hand.** Only reachable by pointing `--out` at a previous
  run's folder; the window and the CLI default to a fresh time-stamped folder every time, and F2 now refuses the
  dangerous half of that configuration (inputs under it). A refusal of a non-empty `outputs/` would be easy, but
  reusing a folder is a choice the user made; left as is.
- **The Tier B "make PART headings bold" fallback.** The audit is right that no generated transform can pass it: V10
  has no bold assertion kind, so a run-boldness change can only fail residual identity. That is the design — a new
  property family needs a verifier-side assertion first (rule 8), and generated code never gets one. It stays
  unsupported until there is an independently verified operation for it; the catalog and the compiler's unsupported
  outcome are the right answer, not Tier B.
- **Its priority order.** F1 and F2 need a multi-folder CLI batch or an input inside the results folder; F5 and F9
  produce wrong documents that PASS in the ordinary single-folder workflow. They were done in that order (F5, F9,
  F1, F2, then the rest), which changes nothing about the result but says where the real exposure was.

## 4. Design notes

- **Output identity.** An input keeps its own name when it is the first with it; a later input with the same
  (casefolded) name gets `stem (n)suffix` for the first `n` no input really has and no earlier output took. Records,
  plans and exceptions carry the output's stem. The rule "a name an input really has is never handed to another
  input" is what makes `Spec (1).docx` safe beside two `Spec.docx`.
- **A run never writes where it reads.** Any input under the results folder is refused before the folders exist. The
  narrower rule (only `outputs/` and `failed/`) would have been enough today and wrong the next time a sub-folder is
  added; the broad rule costs nothing in the window (its results folder gets a time-stamped sub-folder per run) and
  is easy to say.
- **Verify, then write.** The worker holds the output in memory through the suite; `outputs/` receives it only after
  the record exists. A failed record still lands in `outputs/` for the moment between the worker and delivery, as
  before, and is moved to `failed/` before anything is delivered.
- **Continuous means continuous.** Every restart after the cover goes. A later restart is flagged in the plan rather
  than refused, because "make the numbering continuous" on a spec with an appendix that restarts is almost always a
  request to fix the appendix too; the flag is there for the one time it is not.
- **Field depth is a part-wide count.** `field_start_depths` is the transform side's reading of the same rule
  `slots.field_runs` and `verify/template._v_field_runs` already applied to template slots: between a complex
  field's begin and end over the whole part, document order, deleted runs counted.
- **The gate's cost.** Trying a pattern's other files after a refusal is bounded by the batch: in the failure case
  every file of the pattern gets one dry plan (milliseconds each on synthetic specs, under a tenth of a second on a
  thirty-page one); in the success case it stops at the first file that plans. The preview plans every file anyway.
