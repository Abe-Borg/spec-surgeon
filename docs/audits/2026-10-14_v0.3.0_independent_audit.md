# Spec Surgeon v0.3.0 — Independent Audit

Date: 2026-10-14. Branch audited: `claude/stoic-planck-g2x9i0` at commit `bbc1bf2` (identical to `master` for every
file in scope). Input: `Spec_Surgeon_v0.3.0___Independent_LLM_Audit_Specification.xlsx` (three tabs), written by the
LLM that implemented v0.3.0. Deliverables: this report, the filled-in spreadsheet beside it
(`2026-10-14_v0.3.0_audit_checklist_filled.xlsx`), and the probe scripts under `probes/` that reproduce every
finding. **Nothing in `src/` or `tests/` was changed.** Every "suggested fix" below is a recommendation, not a patch.

## 1. Scope and method

For each of the 13 capabilities (tab 1) and 13 invariant/verifier rows (tab 2) I:

1. read the implementation named in "Target Files & Symbols" in full (every file in the tab-3 inventory, plus
   `ops/base.py`, `verify/textcheck.py`, `verify/suite.py`, `tests/make_fixtures.py`);
2. read the test the row cites and ran it;
3. judged three things separately: does the test pass, does the test actually exercise the row's claim, and does the
   implementation honour the hard rules in `CLAUDE.md` (verifier independence, predict-first, identical definitions
   on both sides, V10 covering everything an op changes);
4. wrote independent probes for the claims the author's tests do not cover (negative paths, refusal codes, planted
   defects of my own, transform-vs-verifier agreement on hand-built edge-case documents).

Verdict scale used in column I of tab 1 (and the new column H of tab 2):

| Verdict | Meaning |
|---|---|
| PASS | Implementation matches every claim in the row; tests exercise them; no defect found. |
| PARTIAL | Main path works, but a stated claim is false or overbroad, or there is a meaningful undisclosed gap. |
| FAIL | A stated behaviour is not implemented, or a defect was found that matters. |

## 3. Findings, ranked by severity

Severity: **Medium** = a verification or contract gap that the safety story depends on (no observed data loss);
**Low** = fidelity, usability or documentation; **Info** = worth knowing, no action required.

### F1 · Medium · V4 does not detect duplicate revision ids when the duplicate reuses a source id (AUD-09, V4)

`replace_text` with `allow_tracked_format_split: true` copies the run's `w:rPrChange` onto every split fragment and
gives each copy a fresh `w:id`. The transform does this correctly (probed at the start, middle and end of the
rPrChange run; predicted deltas Δ2/Δ3/Δ2, suite PASS). The **verifier does not enforce it**: `verify/suite.py` V4
builds `collide` only from `(part, kind, id)` tuples absent from the source, and `dup` only from `w:ins`/`w:del` ids.
A planted output whose four `rPrChange` elements all carry the source's id `900` passes V4 (summary says "ids
unique"), V5c and V10 (`_rpr_sig_for_tc` masks the id by design).

This is exactly the shared-failure-mode situation `CLAUDE.md` rule 1 exists for: the safety guarantee is supposed to
come from the check, not from the transform being right. Word tolerates many duplicate ids but they are invalid and
are a known repair trigger.

*Suggested fix (verifier side):* in V4, count every revision element's id in the output across all text parts and
fail on any id that occurs more than once, subtracting only the exact multiset the source already had; keep
`collide` as is. Add a planted-defect test (`probes/probe_chunk3.py` has the mutation).

*Also:* the `ops/replace_text.py` module docstring still says split fragments "drop the duplicate `w:rPrChange`";
the code keeps them with fresh ids. Update the docstring.

### F2 · Medium · The compiler's dry-plan gate accepts specs that plan on zero files (AUD-04)

`compiler._dry_errors` rejects on `FATAL_SPEC_CODES` and, when no representative plans cleanly, on
`PATTERN_SENSITIVE_CODES` (`unfilled-slot`, `expect`, `not-found`, `ambiguous`). Every other refusal code is
silently dropped. The ops raise 22 codes that are in neither set (`spans-runs`, `tracked-format`,
`existing-revisions`, `section-break`, `field-result`, `textbox`, `table-cell`, `inheritance`, `even-odd`,
`title-page`, `structure`, `nested-container`, `conflict-property`, `shared-part`, `slot-structure`,
`slot-in-textbox`, `template-revisions`, `theme-font`, `toggle-ambiguous`, `missing-style`, `pattern`, `internal`).

Probed: a batch whose only representative fails with `spans-runs`, or with `tracked-format`, is **accepted** with
`planned_ok == 0`; an empty batch is accepted too. The row's refusal condition "planned_ok == 0 across all pattern
representatives → reject" therefore holds only for four codes. Nothing is written (the run sets every file aside),
so this is a wasted pass and a misleading "compiled OK", not a loss. Only the positive path is tested.

*Suggested fix:* treat every non-fatal `JobException` as pattern-sensitive (the `else` branch), and reject when
`planned_ok == 0` regardless of code; reject an empty batch explicitly. Add the two negative tests.

### F3 · Medium · Failed-verification outputs stay in `outputs/` beside the passing ones (AUD-05, INV-03)

`batch._process_one` writes the output file before `run_suite` runs, and nothing removes it when verification
fails. Probed with a planted V2 failure: the file is `FAIL`, V9 is "not delivered", `set_aside.json` lists it as
`verify-fail`, and its edited copy sits in `outputs/` next to the PASS copies. The set-aside report says the file was
"safely set aside without changes" and the GUI tells the user "Edited copies: …/outputs (your files were not
changed)". A user who copies that folder onto a project share takes a file that failed verification.

The behaviour predates v0.3.0, but the v0.3.0 reports and the GUI wording make it more likely to bite. Related: the
`verify-fail` code (and most refusal codes) falls back to the generic explanation "The engine refused to guess on
this file's structure and left it untouched", which is wrong for verify-fail (the engine transformed it; only
delivery was withheld).

*Suggested fix:* move a failed output to `outputs/FAILED/` (or delete it and keep the record), and add
`FAILURE_EXPLANATIONS` entries for `verify-fail`, `spans-runs`-adjacent codes, `section-break`, `existing-revisions`,
`structure`, `textbox`, `table-cell`, `bad-params`, `conflict`.

### F4 · Medium-Low · `w:cs` is classified as non-visual noise (AUD-08)

`ooxml.NOISE_RPR_LOCALS = {lang, noProof, snapToGrid, webHidden, cs, eastAsianLayout}`. `w:cs` ("use complex
script formatting on run") makes Word render the run with the `cs` font slot, `w:szCs` size and `w:bCs` weight. Two
runs that differ only by `w:cs` merge under `ignore_formatting_noise`, and the absorbed run loses (or gains) the
flag. Probed: the flag disappears from the merged run, suite PASS (V10 excludes text-edited blocks from the residual
after a run-signature check that the first run's signature satisfies). `eastAsianLayout` and `snapToGrid` also affect
layout in principle. `lang`, `noProof` and `webHidden` are genuinely non-visual.

*Suggested fix:* drop `cs`, `eastAsianLayout` and `snapToGrid` from the noise set (or require `szCs == sz` and no
`bCs`/`iCs` before treating `cs` as noise). Update the README line that lists `w:cs` as non-visual.

### F5 · Low-Medium · The NL compiler cannot discover three v0.3.0 features (AUD-03, AUD-10)

The op catalog the model reads (`catalog.op_catalog()`) still describes `slot_fills` as
`{slot name: {rule: literal|regex|paragraph_after, …}}` and never mentions `first_match`, `occurrence` or
`flexible_whitespace` for slot rules; it lists `expect_checks` by name only and never shows the `{"min": …,
"max": …}` syntax; no worked example uses either. The Pass-2 tests hand the fallback-chain spec in through a fake
client, so nothing proves the live compiler would produce one. Until the catalog is updated, the "rinse and repeat"
loop depends on the model guessing undocumented syntax.

*Suggested fix:* give `slot_fills` a real schema (rule enum incl. `first_match`, `rules`, `occurrence`,
`flexible_whitespace`, `strip`), document ranges under `expect_checks`, and add one worked example per feature.

### F6 · Low · `insert_paragraph` copies only the anchor's `pStyle` (AUD-13)

The new paragraph gets `w:pStyle` (when the anchor has one) and nothing else: no direct paragraph properties
(indent, hanging indent, numbering, tab stops) and no run properties. Probed: inserting after an anchor formatted
directly as Courier New, bold, 9 pt with a 0.5" hanging indent produces `<w:p><w:r><w:t>F.\tNew clause.</w:t></w:r></w:p>`.
In the all-`Normal`, directly formatted documents this release is aimed at, the inserted paragraph will not look like
its neighbours. Also, a tab in `text` is stored as a literal U+0009 inside `w:t` rather than a `w:tab` element; it
renders in LibreOffice (V6 PASS), Word was not tested here.

*Suggested fix:* copy the anchor's `pPr` (minus `sectPr`, `rPr` revision marks and `pPrChange`) and the anchor's
first text run's `rPr` (minus `rPrChange`) onto the new paragraph; predict both and extend the
`inserted_paragraphs` V10 kind to assert them. Consider emitting `w:tab` for `\t`.

### F7 · Low · Tracked `delete_paragraphs` refuses any paragraph that holds a bookmark (AUD-12)

Tracked mode refuses every non-run child with code `structure`. `w:bookmarkStart`/`w:bookmarkEnd` are children of
`w:p`, and Word writes a `_GoBack` bookmark into most saved files. Probed: a paragraph with `_GoBack` is refused in
tracked mode; untracked mode deletes it (and the bookmark) without a flag. Safe, but it will make tracked deletion
fail on a large share of real files.

*Suggested fix:* treat `bookmarkStart`, `bookmarkEnd` and `proofErr` as inert in tracked mode (keep them outside
the `w:del` wrapper); keep refusing `hyperlink`, `sdt`, `smartTag`, comment ranges.

### F8 · Low · Fingerprint and profile claims are overbroad (AUD-01, AUD-02)

- Only `style_regime`, `numbering_regime` and `section_anchor_shape` enter the `pattern_id`. A file whose only mess
  is NBSPs/double spaces in body text keeps the clean file's `b20e6c1da8` (probed), so "messy outliers never hide
  behind a clean file's pattern" is false for whitespace-level mess. By design the sieve still catches such a file
  at plan time, so this is a wording problem, but the compiler never sees that file's profile in Pass 1.
- A tab followed by a space counts as `has_multi_space` (descriptive only). A four-level MasterFormat number
  (`SECTION 21 05 00.13`) classifies as `embedded`, i.e. a separate pattern (conservative).
- `MAX_PROFILE_BYTES` is **6,000** (`profile.py:31`), not the 18,000 the spreadsheet states. `_clip` keeps internal
  NBSP/double spaces but strips a leading or trailing NBSP (`str.strip`).

### F9 · Low · `expect` validation gaps (AUD-03)

`{"min": 5, "max": 1}` and `{"min": -3}` pass validation (the first can never match and always raises `expect` at
plan time); a misspelled `rev_delta` kind (`"delx": 0`) is compared against 0 instead of refused (pre-existing).
The spreadsheet's `property_targets` and `header_footer_slots` are not `expect` checks; a range under either key is
refused as `spec`.

### F10 · Low · Noise merge strips every `w:proofErr` in the edited paragraph (AUD-08)

With `ignore_formatting_noise`, `merge_adjacent_runs` removes all `w:proofErr`/`w:lastRenderedPageBreak` children
of the paragraph, not just those between the runs being merged (probed: 3 → 0 for markers at the far end of the
paragraph). Harmless to content, but unpredicted and unverified: V10 excludes text-edited blocks from the residual.

### F11 · Low · Fill normalisation changes a character (AUD-10)

With `flexible_whitespace` (default true) a fill that contains U+00A0 or a double space is normalised to single
U+0020 on both sides (probed: `WET-PIPE SPRINKLER SYSTEMS` → `WET-PIPE SPRINKLER SYSTEMS`). Both sides agree,
so V10 passes, but the header no longer holds the body's exact characters; a non-breaking space can matter for
line-breaking in a header. Document it, or disable normalisation of the extracted value and normalise only the
match.

### F12 · Info · Documentation and spreadsheet inaccuracies

See §6. None affects behaviour.

### F13 · Info · Test coverage of the v0.3.0 work is positive-path

Of the author's 12 tests, 10 exercise only the success path; the two planted defects mutate the output XML, never
the implementation (`CLAUDE.md` asks for both). None of the refusal codes listed in column F of AUD-12/AUD-13, the
compiler gate's rejection branches, the `first_match` bad-sub-rule rule, or divergence of the four new selectors is
tested. `probes/` contains runnable versions of all of these; they are candidates for `tests/`.
